# Todoアプリ要件定義書（V1）

## 1. 目的・対象範囲

### 1.1 目的
既存のExpress＋TypeScript＋EJSで構成されたWebアプリケーションに、タスク管理（Todo）機能を追加する。学生がNeon PostgreSQLおよびVercelの運用環境を理解し、RESTful APIを通じた非同期通信（Fetch）によるSPA風画面操作の基本を習得することを目的とする。

### 1.2 対象範囲
*   **対象環境・インフラ**
    *   既存のExpress + TypeScript + EJS構成を維持する。
    *   データベースは既存接続設定（`DATABASE_URL`）および学生自身のNeon PostgreSQLを使用する。
    *   Preview環境およびProduction環境は同一のNeon DBを参照する（個人情報は扱わず、架空データのみを使用）。
    *   デプロイ先はVercelとする。
*   **既存機能との兼ね合い**
    *   既存の `/` および `/api/db-check` はそのまま残す。
    *   新規画面は `/todo` パスに配置する。
    *   実際のファイル配置やディレクトリ構造の詳細は確定していないため「要確認」とし、以降の設計書にて決定する。
*   **V1スコープ外**
    *   ユーザー認証・認可機能
    *   優先度（Priority）の設定
    *   表示の絞り込み（フィルタリング）・並び替え機能
    *   Todoタイトルの後からの更新（V1では完了状態の切り替えのみ対応）

## 2. 4機能および受け入れ条件

### REQ-01: Todo一覧取得

*   **概要**: 登録されているTodoの一覧を取得し、画面に表示する。
*   **操作**: 画面（`/todo`）読み込み時、または更新処理後にFetch APIを用いて自動実行する。
*   **入力**: なし（`GET /api/v1/todos`）
*   **結果**: 
    *   ステータスコード `200 OK`
    *   Todo一覧データ（配列）を返却する。データが0件の場合は `data: []` を返却する。
*   **エラー**:
    *   `500 Internal Server Error`: DB接続失敗またはクエリ実行エラー。
*   **受け入れ条件**:
    *   画面初期表示時に登録済みの全Todoがリスト表示されること。
    *   0件の場合はエラーにならず空のリストが表示されること。
*   **確認方法**:
    *   ブラウザで `/todo` にアクセスし、DevToolsのネットワークタブで `GET /api/v1/todos` が `200 OK` で適切なJSONを返しているか確認する。

### REQ-02: Todo新規登録

*   **概要**: 新しいTodoを作成・保存する。
*   **操作**: 画面の入力フォームにタイトルを入力し、追加ボタンを押下する。
*   **入力**: 
    *   `POST /api/v1/todos`
    *   リクエストボディ（JSON）: `{ "title": "文字列" }`
    *   `title` の制約: 前後の空白を除いた長さが 1〜100 文字であること。
*   **結果**: 
    *   ステータスコード `201 Created`（または `200 OK`）
    *   作成されたTodoオブジェクト（ID、title、完了状態など）を返却する。
*   **エラー**:
    *   `400 Bad Request`: リクエストフォーマット不正（JSONパースエラー等）。
    *   `422 Unprocessable Entity`: バリデーションエラー（空文字、100文字超過、空白のみなど）。
    *   `500 Internal Server Error`: DB書き込み失敗。
*   **受け入れ条件**:
    *   有効なタイトルを入力して送信すると、即座に一覧に追加表示されること。
    *   前後空白がトリムされて保存されること。
    *   100文字を超える場合や空文字（空白のみ含む）の場合は登録されず、エラーメッセージが表示されること。
*   **確認方法**:
    *   フォームから正常値および異常値を入力して送信し、レスポンスコードおよび画面上のエラー表示を確認する。

### REQ-03: Todo完了状態の部分更新

*   **概要**: Todoの完了/未完了状態を切り替える。
*   **操作**: 画面上のTodoリスト内のチェックボックスを操作する。
*   **入力**: 
    *   `PATCH /api/v1/todos/:id`
    *   パスパラメータ: `id`（1以上の整数）
    *   リクエストボディ（JSON）: `{ "is_completed": true | false }`
*   **結果**: 
    *   ステータスコード `200 OK`
    *   更新後のTodoオブジェクトを返却する。
*   **エラー**:
    *   `400 Bad Request`: パスパラメータ `id` が数値でない、または1未満の整数。
    *   `404 Not Found`: 指定された `id` のTodoが存在しない。
    *   `422 Unprocessable Entity`: リクエストボディの型不正。
    *   `500 Internal Server Error`: DB更新失敗。
*   **受け入れ条件**:
    *   チェックボックスの変更に応じて、完了状態（打ち消し線表示等）が更新されること。
    *   存在しないIDに対する操作で適切なエラーが返ること。
*   **確認方法**:
    *   画面上のチェックボックスのON/OFFを切り替え、DB状態および画面表示が動的に変わることを確認する。

### REQ-04: Todo削除

*   **概要**: 指定したTodoを削除する。
*   **操作**: 画面上の各Todo項目にある削除ボタンを押下する。
*   **入力**: 
    *   `DELETE /api/v1/todos/:id`
    *   パスパラメータ: `id`（1以上の整数）
*   **結果**: 
    *   ステータスコード `204 No Content`
    *   レスポンス本文なし（Empty Body）。
*   **エラー**:
    *   `400 Bad Request`: パスパラメータ `id` が数値でない、または1未満の整数。
    *   `404 Not Found`: 指定された `id` のTodoが存在しない。
    *   `500 Internal Server Error`: DB削除失敗。
*   **受け入れ条件**:
    *   削除ボタン押下後、該当のTodoが画面一覧から消去されること。
*   **確認方法**:
    *   削除ボタンを押下し、ネットワークタブで `204 No Content` が返り、画面上から要素が消えることを確認する。

## 3. 共通のデータ・エラー条件

### 3.1 REST API構成
すべてのAPIエンドポイントのベースパスは `/api/v1/todos` とする。
画面（`/todo`）からのデータ操作はすべて JavaScript の Fetch API を用いて行う。
※クライアント側の処理分割（`TodoApi` クラス等の設計）については「要確認」とし、詳細設計書にて定義する。

### 3.2 データ入力制約
*   **ID**: 1以上の整数（自動採番）。
*   **Title**: 
    *   型: 文字列
    *   制約: 前後の空白文字（スペース・タブ等）を除外（Trim）した状態で **1文字以上100文字以下**。

### 3.3 共通レスポンス・エラー条件
APIが返却するレスポンス構造およびステータスコードは以下の共通仕様に従う。

*   **成功レスポンス**
    *   `GET` / `POST` / `PATCH`: ステータス `200` または `201` を返し、JSONオブジェクト（データ本体または `data` プロパティ配下）を返却する。
    *   `DELETE`: 成功時はステータス `204` を返し、レスポンス本文は含めない。
*   **エラーレスポンス**
    *   `400 Bad Request`: リクエスト形式の不正、IDの形式不正（非数値や1未満の整数）。
    *   `404 Not Found`: 存在しないリソース（ID）に対する操作。
    *   `422 Unprocessable Entity`: 単体バリデーションエラー（`title` の文字数制限違反や必須項目漏れ）。
    *   `500 Internal Server Error`: サーバー内部エラー、DB接続・クエリ実行失敗。
    *   `503 Service Unavailable`: 外部サービス（Neon DB等）の一時的な利用不可。

## 4. 環境別確認

### 4.1 開発・検証環境（Local / Preview）
*   **環境要件**:
    *   ローカル開発環境およびVercel Preview環境の双方が対象。
    *   データベースは指定されたNeon PostgreSQL（`DATABASE_URL`）を参照する。
*   **確認内容**:
    *   既存エンドポイント（`/`, `/api/db-check`）が影響を受けず正常に動作すること。
    *   `/todo` 画面アクセス時に正常に画面がレンダリングされ、Fetch通信経由で CRUD（4操作）が実行できること。

### 4.2 本番環境（Production）
*   **環境要件**:
    *   Vercel Production環境。
    *   Preview環境と同一のNeon DBを参照する。個人情報等の実データは投入せず、架空のテストデータのみを使用する。
*   **確認内容**:
    *   Vercelへのデプロイ後、本番URL配下の `/todo` で画面操作およびAPI通信が正常に行えること。
