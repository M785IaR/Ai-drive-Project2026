# リアルタイムチャット機能 要件定義書 (`02_requirements.md`)

## 1. 概要・目的・範囲・既存機能との関係

### 1.1. 目的
既存の Express / TypeScript 製 Web アプリケーションに対し、利用者同士がブラウザ上でリアルタイムにメッセージをやり取りできるコミュニケーション機能（`/chat`）を追加する。

### 1.2. 利用者
* **一般ユーザー**: チャットルームへの入室、過去の会話履歴の閲覧、メッセージのリアルタイム投稿を行う利用者。
* **管理者**: チャット機能の稼働監視、定員・接続状況の確認、環境変数および障害対応を行う運用担当者。

### 1.3. 対象範囲（スコープ内）
* `/chat` における EJS テンプレート（`views/chat/index.ejs`）を用いたチャット画面の提供（通常チャット画面および満席時制限画面）。
* `Socket.IO` を用いた同一ルーム内のリアルタイムメッセージ配信。
* 投稿データ（ルーム識別子・ユーザー名・コメント・作成日時）の PostgreSQL（Neon DB）への保存、および初期表示・再接続時の最新20件の取得・表示。
* 1ルームあたり同時接続最大5名の定員制御と、6人目以降の入室・閲覧・投稿の制限。
* 複数インスタンス環境下でのメッセージ同期および全台合計での定員（1ルーム5名）遵守。
* 入力値検証、通信エラー・DB障害時のエラーハンドリング、XSS対策、秘密情報の保護。

### 1.4. 対象外（スコープ外）
* 生成AIによる自動応答・要約・ボット連携機能（既存の `/ai` および `/ai/v2` とは独立した人間同士のチャット専用とする）。
* ユーザーアカウント登録・ログイン認証・パスワード管理機能（既存アプリに認証基盤が存在しないため、入室・投稿時のユーザー名入力のみで識別する）。
* 画像・ファイル添付、スタンプ送信、既読通知、メッセージの編集・削除機能。
* 管理者専用ダッシュボード画面やユーザーバン（強制退室）管理UIの構築。

### 1.5. 既存機能との関係
* **既存ルート・機能への非干渉**: `index.ts` にマウント済みの TOP 画面（`/`）、DB接続確認（`/api/db-check`）、DBサンプル（`/db-sample`）、TODO 機能（`todoRouter`）、AI質問機能（`/ai`, `/api/ai`, `/ai/v2`, `/api/ai/v2`）、および末尾の汎用404ハンドラー・グローバルエラーハンドラーには破壊的変更を加えない。
* **アーキテクチャとDB接続の踏襲**: 既存の TODO アプリ（`src/apps/todo/`）の責務分離（Router / Controller / Service / Model）に倣い、`src/apps/chat/` 配下へ独立ディレクトリとして配置する。DB接続は既存の `db.ts`（`pool`）を共有し、チャット専用テーブル（`chat_messages` 等）を新設して既存テーブル（`products`, `todos`, `ai_qa_logs`, `ai_conversations`, `ai_conversation_turns`）とは分離する。

## 3. 機能仕様詳細

### 3.1. `/chat` の初期表示
* ブラウザが `GET /chat` へアクセスした際、サーバーは対象ルームの現在の参加人数（全台合計）を確認する。
* **参加人数が 5名未満（0〜4名）の場合**:
  * `views/chat/index.ejs` をレンダリングして HTTP `200` で返却する。
  * 画面には「現在の参加人数（例: `2 / 5 人`）」「メッセージ履歴一覧エリア」「ユーザー名入力欄」「コメント入力欄」「送信ボタン」を表示する。
  * 初期表示として、DB に保存されている対象ルームの最新20件のメッセージを取得し、画面下部に最新が来る時系列順（昇順）で表示する。0件の場合は「まだメッセージはありません。」等の案内を正常表示する。

### 3.2. ユーザー名とコメントの入力・送信
* 利用者は「ユーザー名」と「コメント」を入力し、送信ボタン押下（またはフォーム送信）で投稿する。
* フロントエンド（`public/chat/chat.js`）およびバックエンド（`chatController.ts` / `chatService.ts`）の双方で入力検証を実施する。
* 送信処理中は送信ボタンを一時的に無効化し、二重送信を防止する。送信成功時はコメント入力欄のみを空にしてフォーカスを戻し、ユーザー名は連続投稿しやすいよう保持する。

### 3.3. 同じルームへの配信と DB 保存
* サーバーが有効な投稿を受信した際、以下の順序で処理を実行する。
  1. 送信元クライアントが当該ルームの定員枠（5名以内）で正式に入室済みであることを確認する。
  2. 入力値（ユーザー名・コメント）の型・前後空白・文字数上限を検証する。
  3. Neon DB（`chat_messages` テーブル）へ「ルームID・ユーザー名・コメント・作成日時」を保存する。
  4. DB保存の完了後、保存されたレコード（ID・ユーザー名・コメント・作成日時）を `Socket.IO` 経由で同一ルームに接続中の全クライアントへリアルタイム配信する。
* DB保存に失敗した場合はリアルタイム配信を行わず、送信元クライアントへエラー通知を返す。

### 3.4. 初期表示と再接続での最新20件表示
* **初期表示時**: DB から対象ルームの最新20件（`ORDER BY id DESC LIMIT 20`）を取得し、古い順（`id ASC`）に並べ替えて画面に描画する。
* **再接続時**: 一時的なネットワーク断やスリープ復帰等により `Socket.IO` が再接続（`connect` / `reconnect`）された際、切断中に投稿されたメッセージの取りこぼしを防ぐため、サーバーから最新20件の履歴を再取得して画面の履歴一覧を最新状態へ同期する（重複描画は発生させない）。
* 履歴が20件を超える場合、画面上に表示する履歴は常に最新20件までに制限する。

### 3.5. 5人参加中の6人目の画面表示と入室・閲覧・投稿の制限
すでに5名が参加しているルームに対して6人目以降がアクセスした場合、以下の制限を厳格に適用する。
* **画面表示（`/chat` アクセス時）**:
  * チャット本体（会話履歴一覧・ユーザー名入力欄・コメント入力欄・送信ボタン）はレンダリングおよび送信を行わず、代わりに**満席案内画面**（「現在満席（定員5名）のため入室できません。空きが出るまでお待ちください。」およびTOPページへの戻りリンク等）を表示する。
* **入室制限**:
  * 画面表示の瞬間と WebSocket 接続確立の瞬間の時間差で6人目が接続要求を送った場合も、サーバー側の入室処理（`join`）で定員超過を検知して接続を拒否（エラーイベント通知のうえ切断）し、6人目を入室させない。
* **閲覧制限**:
  * 満席状態の6人目には初期履歴（最新20件）を返却せず、またルーム宛てのリアルタイム配信イベント（新規メッセージ）も一切送信しない。
* **投稿制限**:
  * 開発者ツール等から直接メッセージ送信イベントや投稿APIが送られた場合でも、ルーム未入室（定員枠外）のクライアントからの投稿はサーバー側で拒否し、DB保存および他者への配信を一切行わない。
* **退室時の枠解放**:
  * 参加中の5名のうちいずれかがブラウザを閉じる、別ページへ遷移する、または接続が切断された場合、サーバーは当該ユーザーの退室を検知して参加人数を減算し、新たな1名の入室を許可する。

## 4. 非機能要件・セキュリティ・回帰確認基準

### 4.1. 入力値検証（型・前後空白・文字数上限）
* **型検証**: `userName` および `message`（コメント）は文字列（`string`）のみ許可し、数値・オブジェクト・配列・`null` 等は不正入力として拒否する。
* **前後空白の扱い**: 検証前に前後空白（`trim()`）を除去し、除去後の文字列が空文字（0文字）となる入力（半角スペース・全角スペース・改行のみを含む）はすべて拒否する。
* **文字数超過**: Unicodeコードポイント数（`Array.from(trimmed).length`）で上限超過を判定し、超過時はエラーとする（具体的な上限値は第6章にて確定）。
* **リクエストサイズ上限**: HTTP経由のJSON受信時は既存AI機能と同様に `16 KiB` を上限とし、超過リクエストは拒否する。

### 4.2. 通信失敗・DB障害時のエラーハンドリング
* **WebSocket / API 通信失敗**: 接続エラー（`connect_error`）・切断（`disconnect`）・送信タイムアウト発生時、クライアント画面のステータス／エラー領域に分かりやすい日本語メッセージを表示し、自動無限リトライによる負荷増大を防ぐ。送信失敗時は入力中のテキストを消去せず保持し、操作可能状態へ復帰させる。
* **DB障害**: Neon DB への接続失敗・クエリエラー・タイムアウト発生時、サーバープロセスをクラッシュさせず例外を捕捉する。HTTPリクエスト処理中の例外は `next(error)` を通じて `index.ts` のグローバルエラーハンドラーへ連携し、WebSocket処理中の例外はサーバーログへ概要を記録したうえで送信元クライアントへ安全なエラー通知を返す。

### 4.3. 秘密情報の管理
* `DATABASE_URL`、`DATABASE_URL_POOLED`、`REDIS_URL` 等の機密情報は `.env`（ローカル）およびホスティング環境の環境変数のみで管理し、`.gitignore` により Git リポジトリへコミットしない。
* フロントエンド（`views/chat/index.ejs`, `public/chat/chat.js`）およびクライアントへ返却するエラーレスポンスには、接続文字列・APIキー・スタックトレース等の内部情報を一切含めない。

### 4.4. XSS（クロスサイトスクリプティング）対策
* EJS テンプレート（`views/chat/index.ejs`）でサーバー側データを埋め込む際は必ずエスケープ出力（`<%= ... %>`）を使用し、非エスケープ出力（`<%- ... %>`）は使用しない。
* クライアント側 JavaScript（`public/chat/chat.js`）でユーザー名やコメントを DOM へ描画する際は `innerHTML` を一切使用せず、`document.createElement` と `textContent` のみを使用する。

### 4.5. 既存機能の回帰確認（非破壊保証）
チャット機能（ルーター・Socket.IO・DBテーブル）の追加後も、以下の既存機能がすべて従来どおり正常に動作することを回帰確認対象とする。
1. **TOP 画面**: `GET /` が HTTP `200` で正常表示されること。
2. **DB確認・サンプル画面**: `GET /api/db-check` および `GET /db-sample` が正常動作すること。
3. **TODO 機能**: `todoRouter` 配下のタスク一覧表示・追加・更新・削除が正常動作すること。
4. **AI質問機能（V1 / V2）**: `/ai`, `/api/ai/*`, `/ai/v2/`, `/api/ai/v2/*` の画面表示・質問送信・履歴取得・停止スイッチが正常動作すること。
5. **404ハンドリング**: 未定義パスへのアクセスに対し `index.ts` の汎用404ハンドラーが HTTP `404`（`NOT_FOUND`）を返すこと。
6. **グローバルエラーハンドラー**: サーバー内部例外発生時にプロセスが停止せず HTTP `500`（`INTERNAL_SERVER_ERROR`）を返すこと。

## 5. マルチインスタンス対応要件

### 5.1. 複数インスタンス間のメッセージ同期条件
* アプリケーションが複数のサーバープロセス／インスタンスで同時稼働する環境において、異なるインスタンスに接続しているユーザー間でもリアルタイム性と履歴の整合性を保つため、以下のいずれか（または併用）を満たす構成とする。
  * **方式A（Redis Adapter 方式）**: `@socket.io/redis-adapter` と共有 Redis（`REDIS_URL`）を用い、あるインスタンスで受け付けたルーム配信イベントを全インスタンスの Socket.IO サーバーへ自動伝播させる。
  * **方式B（DB同期・再取得方式）**: すべての投稿を単一の Neon DB（`chat_messages`）へ保存し、接続クライアントは定期同期（ポーリング）または再接続時の最新20件再取得によって未受信メッセージを取り込む。
* いずれの方式においても、メッセージの重複表示や順序逆転が起きないよう DB の採番ID（`id`）を基準に整列・重複排除を行う。

### 5.2. 全台合計で1ルーム5人を守る条件
* 各インスタンスのメモリ内変数だけで参加人数を管理すると、インスタンスごとに5名ずつ（例: 2台で合計10名）入室できてしまうため、**全台で共有されるデータストア（Redis または Neon DB）上で現在の参加人数／参加セッションを一元管理**する。
* 入室判定と参加人数の加算はアトミック（排他的・原子的）に行い、2つのインスタンスへ同時に5人目と6人目がアクセスした場合でも、全台合計の参加人数が5名を超過しないことを保証する。
* 異常切断（ブラウザ強制終了やネットワーク断）によって退室通知が届かないケースに備え、ハートビート／有効期限（TTL）によるタイムアウト解放の仕組みを備え、ゴーストセッションが定員枠を永続的に占有しないようにする。

### 5.3. 確認条件（ローカル環境と複数台環境）
* **ローカルで確認する条件（1台・複数ブラウザ／タブ、またはローカル2プロセス）**:
  1. ローカル環境（`npm run dev`）を起動し、異なるブラウザ／シークレットウィンドウを5つ開いて `/chat` に入室し、5名全員間でリアルタイム送受信および最新20件表示が機能することを確認する。
  2. 5名入室中の状態で6つ目のブラウザから `/chat` にアクセスし、満席画面が表示されて入室・履歴閲覧・投稿がすべて制限されることを確認する。
  3. 5名のうち1つのブラウザを閉じた直後、6つ目のブラウザを再読み込みすると入室可能になることを確認する。
  4. ローカルでポート番号を変えた2プロセス（例: `PORT=3000` と `PORT=3001`）を同一の `DATABASE_URL`（および `REDIS_URL`）に接続して起動し、プロセスA（3名）とプロセスB（2名）の合計5名が入室でき、双方間でメッセージが同期されること、さらにプロセスAまたはBへ6人目がアクセスすると満席拒否されることを確認する。
* **複数台で確認する条件（マルチインスタンスデプロイ環境）**:
  1. 本番相当のマルチインスタンス環境（または複数コンテナ／複数サーバー構成）において、環境変数（`DATABASE_URL`, `REDIS_URL` 等）を設定して稼働させる。
  2. 異なるインスタンスに振り分けられたクライアント間で投稿がリアルタイム（または同期方式に応じた規定時間内）に反映されることを確認する。
  3. 複数インスタンスへ分散して合計5名が参加している状態で、いずれのインスタンスへ6人目がアクセスしても満席として入室・閲覧・投稿が拒否されることを確認する。

## 6. 未確定事項・確認事項（「要確認」一覧）

要望書（`01_request.md`）に明記されていない仕様および設計前の決定事項について、提案候補と確認事項を以下に示す。**「要確認」** と記載した項目は設計フェーズ（`03_design.md`）へ進む前に確定させる必要がある。

| 項目 | 候補（提案案） | 確認事項・ステータス |
| :--- | :--- | :--- |
| **1. 文字数上限** | ・ユーザー名: 前後空白除去後 **1〜20文字**（Unicodeコードポイント基準）<br>・コメント: 前後空白除去後 **1〜500文字**（既存AIアプリの2,000文字よりチャット向けに短縮） | **【要確認】** ユーザー名とコメントそれぞれの最大文字数（例: 20文字 / 500文字でよいか、1,000文字まで許容するか）を確定してください。 |
| **2. 参加人数の数え方（複数タブ等）** | ・**案A（Socket接続単位）**: 1ブラウザタブ＝1接続としてカウントする（実装がシンプルで、タブを閉じた瞬間の退室検知が確実）。<br>・**案B（ブラウザ／Cookie単位）**: 同一ブラウザで複数タブを開いても1人と数える（ただし1タブだけ閉じた際の退室判定が複雑になる）。 | **【要確認】** 同一PC・同一ブラウザで複数タブを開いた場合、タブごとに1名と数える（案A）か、ブラウザ単位で1名と数える（案B）かを確定してください。 |
| **3. ルーム数** | ・**案A（固定1ルーム）**: ルーム選択UIは設けず、デフォルトの共通ルーム（`room_id = 'default'`）1部屋のみを提供する（要望書「1部屋あたり最大5名」に最も合致する最小構成）。<br>・**案B（複数固定ルーム）**: 「雑談」「質問」などあらかじめ用意された2〜3部屋から選択できる形式にする。 | **【要確認】** 初版実装では固定1ルーム（案A）とするか、複数の固定ルーム（案B）を用意するかを確定してください。 |
| **4. 満席時の再試行方法** | ・**案A（手動再試行）**: 満席画面に「空き状況を再確認（再読み込み）」ボタンを配置し、利用者が押下したタイミングで再度入室判定を行う（不要な通信負荷が発生しない）。<br>・**案B（自動待機・再試行）**: 満席画面を開いたまま一定間隔（例: 10秒ごと）で空きを確認し、空きが出たら自動入室する。 | **【要確認】** 満席時の再試行は利用者の手動操作（案A）とするか、自動ポーリングによる待機入室（案B）とするかを確定してください。 |
| **5. ファイル配置先とサーバー統合構成** | ・**アプリモジュール**: `src/apps/chat/`（`chatRouter.ts`, `chatController.ts`, `chatService.ts`, `chatModel.ts`）<br>・**ビュー / 静的**: `views/chat/index.ejs`, `public/chat/chat.js`, `public/chat/chat.css`<br>・**SQL**: `sql/chat/040_create_chat_messages.sql`<br>・**サーバー起動統合**: 既存構成は `index.ts` に `app.listen(...)` が直接記述されており `local.ts` は存在しないため、`http.createServer(app)` を `index.ts` 内に導入して `Socket.IO` をアタッチする構成を候補とする。なお、Vercel 等のサーバーレス環境では WebSocket の常時接続維持に制約があるため、ホスティング環境の前提確認が必要。 | **【要確認】** ① `index.ts` を `http.createServer(app)` ベースに変更して `Socket.IO` を統合してよいか、② 実際のデプロイ環境が常時稼働サーバー（Render / Railway / VPS 等）かサーバーレス（Vercel 等）か（それにより Redis Adapter 必須か DB同期併用かが決まるため）を確認してください。 |
