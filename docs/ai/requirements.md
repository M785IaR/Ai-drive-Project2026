# AI質問機能 開発対象範囲および確認事項整理

## 1. 要望一覧と開発対象範囲（WISH-AI-*）

`docs/ai/request.md` の記述に基づき、追加要望を `WISH-AI-*` として整理・分類した表は以下の通りです。

| 要望ID | 利用者がしたいこと | 必須・発展 | 具体化が必要な点 |
| :--- | :--- | :--- | :--- |
| **WISH-AI-001** | AI質問画面（UI）から質問テキストを入力し、AIの回答を確認したい | 必須 | ・画面構成（完全独立ページか、既存画面へのセクション追加か）<br>・画面上のデザイン・レイアウト詳細 |
| **WISH-AI-002** | 送信した質問に対して、バックエンド経由でAI（LLM）からの回答を受け取りたい | 必須 | ・利用する外部AI APIの選定（OpenAI API / Anthropic API 等）<br>・APIのモデル指定およびタイムアウト設定等のパラメータ |
| **WISH-AI-003** | 通信エラーや入力値不正（空文字等）が発生した際に、適切なエラーメッセージを表示してほしい | 必須 | ・フロントエンド側でのバリデーションルール<br>・表示するエラーメッセージの文言と表示形式（アラート、インライン表示等） |
| **WISH-AI-004** | APIキー等の機密情報を安全に管理した環境で利用したい | 必須 | ・環境変数名（`AI_API_KEY`等）の正式決定<br>・ローカル開発・本番環境での環境変数設定手順の共通化 |
| **WISH-AI-005** | 既存のTODO機能やアプリケーション全体の動作に影響を与えずにAI機能を利用したい | 必須 | ・既存のルーティングやミドルウェアとの干渉防止（`src/apps/ai/` でのディレクトリ隔離） |

※現時点でログイン機能、会話履歴の保存・記憶機能、Markdown表示切り替えなどの機能拡張は本スコープに含まれておりません。

---

## 2. 確認が必要な点（最大5件）

仕様確定のために clarification が必要な主要5項目について整理しました。各項目において「確定事項」と「提案（検討案）」を区別して記述しています。

### 1. 質問長の上限・バリデーション
* **確定事項**: `request.md` にて、空文字などの入力値不正に対してエラーハンドリングを行うことが決定しています。
* **提案**: 外部APIのトークン消費抑止およびレスポンス遅延防止のため、フロント・バックエンド双方で文字数制限（例: 最短1文字〜最大1,000文字）を設けることを提案します。

### 2. 会話履歴の扱い（履歴件数）
* **確定事項**: `request.md` の現行要件には、過去の会話履歴をAIのコンテキストに含める旨の記述はありません（1問1答形式が基本）。
* **提案**: 初版実装としては「履歴件数 0件（過去ログを含めない単発の質問・回答）」で進めることを提案します。

### 3. 保存成功の定義（データの永続化）
* **確定事項**: `request.md` には、データベース（DB）への質問・回答ログ保存に関する明示的な要件は記載されていません。
* **提案**: 今回のスコープにおける「処理成功」の定義は、「DB保存」ではなく「外部AI APIの呼び出し成功およびクライアントへの回答レスポンス完了」とすることを提案します。（DB保存が必要な場合は、要件追加として検討が必要です。）

### 4. 失敗時の動作・フォールバック
* **確定事項**: `request.md` にて、API通信エラーや不正値発生時にユーザーフレンドリーなエラーメッセージを表示し、サーバーがクラッシュしないよう例外処理を行うことが決定しています。
* **提案**: HTTPステータスコード（400: バリデーションエラー、500/504: AI API側エラー）を明確に区分し、画面上には「AIサービスの呼び出しに失敗しました。時間をおいて再度お試しください」といった統一されたメッセージをインライン表示する挙動を提案します。

### 5. 公開条件・環境設定
* **確定事項**: APIキー等の機密情報は `dotenv` を用い、環境変数から読み込むことが決定しています。
* **提案**: アプリケーション起動時（サーバー立ち上げ時）に `AI_API_KEY` が未設定の場合は、起動時ログに警告を出力するか、該当機能呼び出し時に即座に安全なエラーを返却する仕組みを公開条件（動作要件）とすることを提案します。
