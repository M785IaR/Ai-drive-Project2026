# AI質問アプリ V2 要件定義書

* **保存先**: `docs/ai/v2/requirements.md`
* **対象システム**: AI質問アプリ V2（会話継続・話題別管理機能）
* **作成日**: 2026-11-25

---

## 1. 目的・利用者・開始条件

### 1.1 目的
V1（単発の質問と回答の履歴表示）の基盤を引き継ぎ、利用者が話題ごとに複数の会話スレッドを作成・切り替えながら、過去のやり取りの文脈を踏まえてAIと対話を継続できるWebアプリケーション機能（V2）を追加する。

### 1.2 利用者
* V1の実Gemini API接続およびデータベース保存を確認済みの単一利用者（実習履修者・評価者）。
* 認証機構を持たない単一利用者環境を前提とし、実習・検証データには架空の内容のみを使用する（個人情報は入力しない）。

### 1.3 開始条件
本開発・検証を開始するための前提条件は以下のとおりとする。
1. V1アプリがローカル環境で起動できること。
2. Express経由で実際のGemini APIから回答を取得し、HTTP `201` 応答とデータベース（`ai_qa_logs`）への履歴保存が確認済みであること。

---

## 2. 対象範囲（必須要件と発展課題の区分）

### 2.1 対象範囲（今回実装する必須機能）
* 話題ごとの新規会話作成および会話一覧の取得・切り替え機能
* 選択した会話における履歴表示（最新20往復・古い順）
* 選択した会話の直近文脈（最新5往復・古い順＋今回の質問）を付与したGemini APIへの質問送信および1往復単位のDB保存
* 画面再読み込み後の会話一覧再取得および選択した会話の再開
* 入力値・本文サイズ検証、エラー時の入力保持と操作復帰、自動再送抑止
* 既存機能（V1の画面・API・履歴、TOP画面、TODO機能）の維持および公開環境でのV2 API停止制御

### 2.2 対象外（発展課題）
授業の共通条件に基づき、以下の機能はV2必須範囲の対象外（発展課題）とする。
* ログイン認証機能
* ユーザー別の権限管理・データ分離
* 作成済み会話名の変更機能
* 会話または個別往復の削除機能
* V1の既存履歴（`ai_qa_logs`）からV2会話データへの移行機能

## 4. 機能要件（REQ-V2-01 〜 REQ-V2-06）

### REQ-V2-01：新規会話の作成と会話一覧からの切り替え
* **対応WISH**: WISH-V2-02
* **根拠**: 変更要望 WISH-V2-02、授業の共通条件（会話IDで会話を区別する／会話名は前後空白を除き1〜50 Unicodeコードポイント）
* **要件**:
  * 利用者は会話名を入力して新しい会話を作成でき、システムは一意の会話IDを発行してデータベースに保存する。
  * 作成済みの会話一覧を取得して画面に表示し、利用者が任意の会話を選択して切り替えられるようにする。
* **受入条件**:
  1. 会話名「話題A」と「話題B」の2件を新規作成すると、それぞれ異なる会話IDで保存され、会話一覧の両方に表示されること。
  2. 一覧から「話題A」と「話題B」を交互にクリック（選択）した際、現在選択中の会話が切り替わること。

### REQ-V2-02：選択中会話の履歴表示（最新20往復）と再読み込み後の再開
* **対応WISH**: WISH-V2-02, WISH-V2-03
* **根拠**: 変更要望 WISH-V2-02・03、授業の共通条件（選択中の会話の最新20往復を古い順に表示する）
* **要件**:
  * 選択中の会話に紐づく保存済み履歴から**最新20往復**を取得し、画面上には**古い順（時系列順）**で表示する。
  * 新規作成した直後など履歴が0件の会話はエラーとせず、正常な0件状態として表示する。
  * ブラウザを再読み込み（F5等）した後も、会話一覧を再取得し、保存済みの会話を選択して過去の履歴表示および追加質問を再開できる。
* **受入条件**:
  1. 新規作成した空の会話を選択した際、エラーにならず正常な0件状態として表示されること。
  2. 21往復以上のやり取りがある会話を選択した際、画面には直近の20往復のみが古い順（上から下へ時系列順）に表示されること。
  3. やり取りを保存した後にブラウザを再読み込みし、会話一覧から該当の会話を再度選択すると、保存されていた履歴が再取得されて表示され、続けて質問できること。

### REQ-V2-03：同じ会話の文脈継続（Geminiへの最新5往復送信）
* **対応WISH**: WISH-V2-01, WISH-V2-03
* **根拠**: 変更要望 WISH-V2-01・03、授業の共通条件（Geminiには同じ会話の保存済み最新5往復を古い順に並べ、今回の質問を末尾に加えて渡す。新規会話の初回は今回の質問だけを送る）
* **要件**:
  * 選択中の会話で質問を送信する際、サーバーは同じ会話IDに属する保存済みの**最新5往復**を取得し、**古い順（質問→回答のペア順）**に並べて文脈を組み立て、末尾に今回の質問を追加してGemini APIへ送信する。
  * 画面表示の上限（最新20往復）と、Gemini APIへ送信する文脈の上限（最新5往復）を明確に区別して処理する。
  * 新規会話の1回目の質問送信時は過去履歴が存在しないため、今回の質問のみをGemini APIへ送信する。
* **受入条件**:
  1. 会話Aの1回目で架空の合言葉（例：「合言葉は『しろくま47』です」）を送信して保存した後、同じ会話Aの2回目で「さっきの合言葉は何ですか？」と質問すると、直前のやり取りを踏まえた回答（『しろくま47』に言及した応答）が返ること。
  2. 6往復以上の履歴がある会話で追加質問を行った際、Geminiへ渡される過去文脈が最新5往復分（古い順）＋今回の質問に制限されていること。

### REQ-V2-04：別会話への文脈・表示混入の防止
* **対応WISH**: WISH-V2-02
* **根拠**: 変更要望 WISH-V2-02、授業の共通条件（会話IDで会話を区別する／新規会話の初回は今回の質問だけを送る）
* **要件**:
  * 履歴の取得・表示およびGemini APIへ渡す文脈の組み立ては、すべて選択中の会話IDのみを条件として絞り込む。
  * ある会話の履歴や送信文脈が、別の会話の表示やAI応答に混入しないようにする。
* **受入条件**:
  1. 会話Aに架空の合言葉を記憶させた状態で新しい会話Bを作成し選択した際、会話Bの画面に会話Aの履歴が表示されないこと。
  2. 会話Bの初回送信で「さっきの合言葉は何ですか？」と質問した際、Geminiへ渡される内容は今回の質問のみであり、会話Aの合言葉を前提とした回答が返らないこと。

### REQ-V2-05：入力検証・保存原子性・失敗時の安全性
* **対応WISH**: WISH-V2-01
* **根拠**: 授業の共通条件（会話名は前後空白を除き1〜50 Unicodeコードポイント、質問は1〜2,000 Unicodeコードポイント、JSON本文は16 KiB以内／質問と回答は1往復として保存し、両方が成功してから201を返す／失敗時は入力を残して再操作できる状態に戻し、自動再送はしない）
* **要件**:
  * **入力・サイズ検証**:
    * 会話名は前後空白を除いた状態で **1〜50 Unicodeコードポイント** であること。
    * 質問文は前後空白を除いた状態で **1〜2,000 Unicodeコードポイント** であること。
    * APIリクエストのJSON本文サイズは **16 KiB以内** であること。
    * 不正な会話ID、存在しない会話ID、または上記検証違反の場合はGemini APIを呼び出さずエラー応答を返す。
  * **保存と応答の整合性**:
    * 質問とAI回答は1往復としてセットでデータベースに保存し、**Geminiからの有効な回答取得とDB保存の両方が完了した後にのみ HTTP `201`** を返す。
    * Geminiの通信失敗・タイムアウト・空回答、またはDB保存失敗が発生した場合は未完了・不完全データを保存せず、エラー応答を返す。
  * **失敗時のUI復帰と再送抑止**:
    * エラー発生時は入力欄の文字列（会話名・質問文）を消去せず保持し、通信中の操作ロックを解除して利用者が再操作できる状態へ戻す。
    * ブラウザ側・サーバー側SDKともに自動再試行（リトライループ）を行わない。
* **受入条件**:
  1. 空文字や51コードポイント以上の会話名、空文字や2,001コードポイント以上の質問、16 KiB超のJSONを送信した場合にエラーとなり、Gemini APIが呼ばれないこと。
  2. 存在しない会話IDを指定して質問送信した場合にエラー（`404`）となり、DB保存もGemini呼び出しも行われないこと。
  3. 正常に回答取得とDB保存が完了した場合のみ HTTP `201` が返ること。
  4. API障害や空回答・保存失敗時に `201` が返らず、入力欄のテキストが残ったまま再送信可能な状態へ復帰し、勝手に再送リクエストが飛ばないこと。

### REQ-V2-06：既存機能の維持と公開環境でのV2 API停止制御
* **対応WISH**: 共通基盤要件
* **根拠**: 授業の共通条件（V1のExpress／TypeScript・Neon・Gemini APIを引き継ぎ、既存の画面・API・履歴とTOP・TODOは維持し、V2を追加する／評価は原則ローカルで行い、公開環境ではV2のAPIを停止する）
* **要件**:
  * V2の追加によって、既存のTOP画面、TODO機能、およびV1の画面・API・履歴データ（`ai_qa_logs`）の動作を破壊しないこと。
  * 公開環境（または停止設定時）において、V2のAPI群を安全に停止（`503` 応答等で外部AI呼び出し・DB更新を遮断）できる制御機構を備えること。
* **受入条件**:
  1. V2実装後も、TOP画面、TODO機能、およびV1の画面・質問送信・履歴表示が従来どおり正常動作すること。
  2. V2停止設定を有効にした状態でV2のAPIへアクセスすると停止エラー（`503`）が返り、かつその状態でもV1・TOP・TODO機能は正常に動作すること。

## 5. データ要件・運用要件

### 5.1 データ要件
* **技術基盤**: PostgreSQL（Neon）を引き続き使用する。
* **データ分離**: V1の履歴テーブル（`ai_qa_logs`）とは独立したV2専用のテーブル構造（会話テーブルおよび会話往復テーブル）を設け、会話IDによる外部キー関連付けを行う。
* **取得・並び順の区別**:
  * 画面表示用取得：指定会話IDの最新20往復を取得し、古い順（昇順）に並べて返却する。
  * Gemini文脈用取得：指定会話IDの保存済み最新5往復を取得し、古い順（昇順）に並べてプロンプト文脈を構築する。
* **実習データ**: テスト・動作確認に使用する会話名および質問文は架空の内容とし、個人情報や機密情報を含めない。

### 5.2 運用・セキュリティ要件
* **秘密情報管理**: `GEMINI_API_KEY`、`DATABASE_URL` 等の機密情報はサーバー側の環境変数のみで管理し、クライアント側JS・HTML・APIエラー応答・Gitリポジトリへ露出させない。
* **安全な描画（XSS対策）**: ブラウザ側での会話名・質問文・AI回答の表示には `textContent` 等の安全なDOM操作を使用し、HTMLインジェクションを防止する。
* **公開環境での運用**: 評価は原則ローカル環境で実施し、公開環境（Preview / Production）ではV2 APIを停止状態にして意図しないAPI利用・課金を防ぐ。
