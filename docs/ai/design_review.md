# 要件定義書・設計書 照合・レビュー結果 (`docs/ai/design_review.md`)

要件定義書（`docs/ai/requirements.md`）および基本・詳細設計書（`docs/ai/spec.md`）の内容を照合し、セキュリティ、処理順序、エラーハンドリング、一貫性、およびトレーサビリティの観点から詳細レビューを実施しました。

---

## 1. チェックリスト結果サマリー

| チェック項目 | 評価 | 主な確認結果・備考 |
| :--- | :---: | :--- |
| **1. ブラウザへの秘密情報遮断** | **適合** | APIキーやDB接続情報は Express（バックエンド）のみで扱い、ブラウザには露出していません。 |
| **2. 入力検証とAI呼出し順序** | **適合** | `aiController` で文字数・空文字バリデーションを行った後に `aiService` を呼び出す構成になっています。 |

| **4. 履歴0件の扱い** | **適合** | 会話履歴を送信せず、単発の質問・応答（1問1答）として処理する設計になっています。 |

## 2. 検出された問題点と修正案

### 項目A: 【一貫性】環境変数名の表記揺れ
* **対象ID**: `REQ-AI-N002`, `DES-AI-006`
* **問題点**: 
  要件定義書および要望書では環境変数名が `AI_API_KEY` となっているのに対し、設計書（`spec.md` の1, 7, 9章）では `GEMINI_API_KEY` と記載されています。実装時の誤解を招く可能性があります。
* **修正案**: 
  全文書で環境変数名を `AI_API_KEY`（または Gemini 採用に合わせて `GEMINI_API_KEY`）に統一します。本プロジェクトでは **`GEMINI_API_KEY`** に一意化することを推奨します。

---

### 項目B: 【例外処理】AI成功・DBログ保存失敗時の動作非決定
* **対象ID**: `REQ-AI-F004`, `REQ-AI-D001`, `DES-AI-004`, `DES-AI-008`
* **問題点**: 
  Gemini API から正常に回答を取得できたものの、SQLite へのログ保存（`aiModel.createLog`）が失敗した場合に、クライアント（ブラウザ）へエラー（500等）を返すべきか、それともAIの回答自体は正常返却（200 OK）としログ失敗のみサーバーログに記録して無視するかの判断が仕様化されていません。
* **修正案**: 
  `spec.md` の第8章に以下を追記します。
  > **DBログ保存失敗時のフォールバック**: 
  > データベースへのログ記録 (`ai_qa_logs`) に失敗した場合でも、AIからの回答生成が成功している場合はクライアントに HTTP 200 OK で回答を返却する。ログ保存失敗はサーバー側ログに出力（`console.error`）し、非同期処理の例外としてレスポンス処理を遮断しない。

---

### 項目C: 【処理順序】デモモード動作時の処理フロー明確化
* **対象ID**: `REQ-AI-F002`, `DES-AI-002`, `DES-AI-005`
* **問題点**: 
  `spec.md` 第9章で「`GEMINI_API_KEY` 未設定時はデモモードで動作」と規定されていますが、デモモード時に「入力バリデーションを実行するか」「外部API呼出しを行うか」「DBログを保存するか」のステップ順序が明示されていません。
* **修正案**: 
  `aiService` 内の処理フローとして以下を明確に規定します。
  1. 入力バリデーション実行（デモ時も文字数チェック等は適用）
  2. デモモード判定（`GEMINI_API_KEY` 未設定の場合、外部 Gemini API 呼出しを行わず定型デモ応答を取得）
  3. DBログ保存処理（ステータス `DEMO` または `SUCCESS` として記録）

---

### 項目D: 【確認方法】履歴0件時の動作テスト仕様の補足
* **対象ID**: `REQ-AI-F002`, `DES-AI-002`
* **問題点**: 
  1問1答形式（過去ログを参照しない仕様）が機能していることの検証手順が `spec.md` 第10章の確認方法に含まれていません。
* **修正案**: 
  `DES-AI-002` の検証方法に以下を追加します。
  > 連続して質問を送信した際、前回の質問文や回答文が Gemini API へのリクエストボディ（プロンプト）に含まれず、独立した単発リクエストとして処理されていることをログまたはテストケースで確認する。

---

## 3. 総合評価

上記の指摘事項（項目A〜D）を補正することにより、要件定義と設計間の整合性が完全に確保され、コード実装フェーズへ安全に移行できる設計品質となります。
